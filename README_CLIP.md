## Архитектура

- Изображение → CLIP ViT-B/32 → 512-мерный нормированный вектор.
- Русский/английский запрос → multilingual DistilBERT, дистиллированный в
  пространство этого CLIP → 512-мерный нормированный вектор.
- Изображение → Qwen2.5-VL-7B → визуальное описание, эмоция, стиль, OCR.
  Эти тексты кодируются тем же мультиязычным текстовым энкодером.
- Baseline: cosine(query, image). Альтернативы: OCR TF-IDF, гибрид трёх ветвей.
- Обучение: residual MLP rank=64 для запроса и картинки; веса смешивания трёх
  ветвей. Backbone заморожен. Multi-positive InfoNCE, temperature=0.07,
  AdamW, lr=0.001, до 10 эпох, best checkpoint по dev NDCG@5.
- Поиск: точное матричное произведение. При 30 тыс. × 512 один FP32-массив
  занимает около 61 MB; ANN/FAISS не требуется для первого решения.
- Генерация: перевод запроса на английский → готовый FLUX.1-schnell (4 шага) →
  удаление фона U2Net через rembg → RGBA PNG. Генератор не дообучается.

DINO не выбран основой: его визуальные представления не дают готового общего
пространства с текстовыми запросами. CLIP выбран как воспроизводимый baseline,
а не как доказанно лучшая современная модель. SigLIP 2 реализован в отдельном
[эксперименте](docs/SIGLIP2.md), ожидающем GPU-запуска. Связь с курсом: лекции 5 (metric
learning), 6 (CLIP/DINO/SigLIP), 9 (OCR), 12 (мультимодальные модели).

## Установка

Linux, Python 3.10–3.12; для подготовки и поиска достаточно CPU. Для разметки
предполагается узел с 4 × A100 80 GB. Скрипт разметки делит данные между четырьмя
независимыми процессами, по одной модели на GPU. Для поиска и обучения адаптеров
достаточно одной GPU. Проверьте свободное место для данных, весов и их временных архивов. При переносе
в этом запуске раздел 147 GB заполнился из-за одновременного хранения копий;
использовался отдельный раздел для больших архивов. Размер индекса гораздо меньше весов.

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
# Сначала установить подходящую CUDA/CPU-сборку torch и парный torchvision.
# Для согласованного профиля этого пода (CUDA 12.8):
python -m pip install -r requirements/cuda-cu128.txt --index-url https://download.pytorch.org/whl/cu128
python -m pip install -e '.[demo,generation,yt,test,report]'
python -m pytest -q
```

Большинство прямых зависимостей закреплены в pyproject.toml. Torch допускает
2.7.1–2.9.x, чтобы сохранить подходящую сборку из образа; конкретный CUDA-профиль
закреплён в `requirements/cuda-cu128.txt`. Если после старой установки появился
`torch==2.7.1+xpu`, из корня проекта выполнить `bash scripts/repair_cuda.sh`.
Этот скрипт восстанавливает исходный для данного пода 2.9.1+cu128; в этом запуске
CUDA-проверка на всех четырёх A100 пройдена. Ревизии моделей — commit SHA в
`configs/model_revisions.json`. Для точного повторения своей GPU-среды сохраните
`python -m pip freeze > runs/environment.txt`, `nvidia-smi` и версию CUDA образа.
CPU-проверка в этой поставке имеет отдельный фактический `evidence/environment.txt`.
Транзитивные зависимости GPU-среды пока не зафиксированы lock-файлом.

## 1. Подготовка каталога на машине с интернетом

```bash
python -m sticker_search.prepare \
  --nyu-count 30000 --synth-cards --output data/catalog
python -m sticker_search.audit --catalog data/catalog --output evidence/catalog
```

Источники:

| Источник | Использование | Условия, заявленные автором набора |
|---|---|---|
| [nyuuzyou/stickers](https://huggingface.co/datasets/nyuuzyou/stickers) | 30 тыс. статичных PNG из valid.zip (6.6 GB), emoji-метки | WTFPL |
| [StickerQueries](https://huggingface.co/datasets/metchee/sticker-queries) | До 578 PNG из английской части, человеческие поисковые запросы | MIT |
| [Synth-GCD](https://huggingface.co/datasets/gauravs101/synthetic-greeting-cards) | 100 синтетических открыток, английский текст внутри изображения | Apache-2.0 |
| [OpenMoji](https://openmoji.org/) | Опциональные 240 шаблонных открыток из пилота этапа 1 | CC-BY-SA-4.0, атрибуция обязательна |

Для включения старых OpenMoji-карточек добавьте `--pilot /path/to/stage1_project`.
Они имеют 24 независимых исходных рисунка; варианты шаблонов не считаются
независимыми сюжетами. В варианте без `--pilot` их нет — это другой состав каталога.
Точный состав поставленного запуска фиксируется `data/catalog/build_config.json`.
Для восстановления именно поставленного каталога (включая выбранные группы и
OpenMoji-карточки), а не новой выборки:

```bash
python -m sticker_search.restore_catalog --output data/catalog
```

Используется `evidence/full_catalog/manifest.jsonl` и проверяется SHA-256 каждого
изображения. Полный многогигабайтный корпус в архив с кодом не включён; готовый
CPU-пилот из 472 изображений включён в полный проектный ZIP (`data/cpu_pilot`).
В архиве для Git размещены только 240 необходимых для точного восстановления
OpenMoji-композиций в `evidence/openmoji_pilot/images`; именно их использует
`restore_catalog` по умолчанию. Атрибуция сохранена в `evidence/full_catalog/licenses`.

Лицензия карточки датасета не является независимой проверкой прав на каждого
стороннего персонажа или рисунок. Сохраняем происхождение каждого файла и не
публикуем весь собранный корпус автоматически. Код проекта и данные разделены.

Повторный запуск с теми же параметрами использует кеш. Смена параметров требует
нового `--output`. Неполная загрузка завершается ошибкой и сохраняет список
неудач; повторите ту же команду. `--nyu-count 0 --sq-limit 100` даёт маленький
пробный набор. Первый архив nyuuzyou всё равно скачивается целиком при count>0.
Более 33 тыс. уникальных изображений потребует подключения другого исходного
архива: эта версия не притворяется, что valid.zip содержит 100 тыс. изображений.

Дубликаты: нормализованный RGBA pixel SHA-256; группировка визуально близких
изображений по dHash<=3, близким пропорциям и среднему цвету. Известные семьи
OpenMoji объединяются. Кандидаты dHash дополнительно проверяются на обрезанных
по содержимому миниатюрах 64×64: IoU foreground-масок >=0.85 и RGB MAE<=0.03.
Это добавлено после обнаружения ложной группы из 360 разных стикеров с большими
пустыми полями. Telegram pack_id в источнике не предоставлен, поэтому
группировка эвристическая и требует аудита. Разбиение 70/15/15 по хешу группы.
Исходный valid.zip используется как сырьё; это НЕ оценка на официальном source split.

## 2. Перенос через YT

Токен храните в окружении или стандартной конфигурации YT. Не добавляйте его
в README, репозиторий или сообщение чата.

```bash
export YT_PROXY='ВАШ_КЛАСТЕР'
export STICKER_YT_DIR='//home/ВАШ_ПУТЬ/sticker_project/v1'
python -m sticker_search.pack pack --input data/catalog --output data/bundle
python -m sticker_search.yt_transfer upload --local data/bundle --remote "$STICKER_YT_DIR"
```

На GPU-узле с теми же переменными:

```bash
bash scripts/restore_from_yt.sh
```

Архивы по 500 изображений содержат пути `images/...`, manifest, разметку и
контрольные суммы. Загрузка выполняется в локальный каталог перед инференсом;
обучение не делает удалённые запросы в YT для каждого изображения.
Существующие отличающиеся файлы YT не перезаписываются. Используйте новый каталог
версии. В этом проекте перенос через рабочий YT выполнен; в новой среде нужно задать собственные параметры доступа.

Веса также нужны локально. Если GPU-узел без интернета, скачайте закреплённые
ревизии в Hugging Face cache на доступной машине, перенесите cache как отдельный
артефакт, задайте `HF_HOME` и `HF_HUB_OFFLINE=1`. Кеш должен сохранять структуру
snapshots/blobs. Скачивание только весов без tokenizer/processor недостаточно.

```bash
HF_HOME=/path/to/cache python scripts/cache_models.py --preset all
```

Для генерации без интернета перенесите также `~/.u2net` или задайте `U2NET_HOME`.
Файл модели U2Net скачивается rembg отдельно от Hugging Face.

## 3. Пробная разметка 500 изображений на 4 GPU

```bash
python -m torch.distributed.run --standalone --nproc_per_node=4 \
  -m sticker_search.annotate --task caption --catalog data/catalog \
  --output runs/captions_500_v2 --limit 500 --batch-size 8
python -m sticker_search.annotate --task caption --catalog data/catalog \
  --output runs/captions_500_v2 --merge
```

Проверить глазами 50–100 примеров: ошибки OCR, выдуманные предметы, эмоции,
разницу между буквальным описанием и предполагаемой ситуацией использования.
Время полного запуска оценивать по полученной скорости, а не обещать заранее.
`timing-rankXX.json` хранит реальные измерения. При OOM уменьшить batch-size.
Ошибки JSON не принимаются молча: сохраняются в errors; успешные записи кешируются.
Повторный запуск повторяет пропущенные записи. Число процессов при resume не менять.
Для удобного просмотра:

```bash
python -m sticker_search.review_annotations --catalog data/catalog \
  --annotations runs/captions_500_v2/annotations.jsonl --output runs/review_500_v2.html
```

В версии prompt v2 явно запрещены вопросы анализа изображения и инструкции
по рисованию. В пилоте отдельно проверить `usage_queries_ru`: это короткие запросы
на подбор стикера («кот машет лапой», «поздороваться»), а не «Как нарисовать?»
или «Что означает надпись?». Это всё ещё слабые метки, требующие проверки.

Новый prompt меняет хеш конфигурации. Использовать новый каталог `captions_500_v2`;
старые результаты не удалять и не смешивать с новыми. Для восстановления старого
пилота из ошибок `Invalid OCR language` см. `docs/POD_RUNBOOK.md`, раздел 5.1.
Восстановление на CPU сохраняет исходный хеш prompt и не улучшает смысл запросов.

Затем полный запуск после проверки качества запросов (отдельный каталог вывода):

```bash
bash scripts/run_gpu.sh
```

Скрипт последовательно выполняет полную разметку, перевод исходных запросов,
эмбеддинги, обучение и оценку на dev отдельно для EN/RU. Вывод — `runs/full_v2`
(можно задать `STICKER_RUN_ROOT`). После аудита v2 синтетические `usage_queries_ru`
исключены из этого опыта; VLM-описания/OCR используются как признаки. Адаптер
обучается на исходных запросах и их переводах. Финальная test-оценка уже выполнена и сохранена в `evidence/final_v1`.
Результаты аудита: `evidence/caption_review/annotation_review_comparison.html`.
Отдельный просмотр открыток создаётся в `runs/full_v2/review_postcards.html`.
Парсер v3 и повторный проход с лимитом 1024 обрабатывают только недостающие
caption-ответы. Если остаётся не более 0,5% пропусков, эти картинки сохраняются в
индексе с визуальными признаками; точное покрытие и ID находятся в
`runs/full_v2/captions/coverage.json`. Строгий merge без явного разрешения
частичного покрытия по-прежнему требует все строки. Инструкция продолжения
после 30 863/30 914 — `docs/POD_RUNBOOK.md`, раздел 5.2.
Для продолжения с переводов после готового caption-этапа:
`bash scripts/run_gpu.sh --from translate`. Этот режим сохраняет готовые описания,
повторяет только отсутствующие переводы с лимитом 512 и затем запускает индекс,
обучение и оценку. Если строгий merge переводов не проходит, полные ответы ошибок
сохраняются в `runs/full_v2/translations/failures_latest.jsonl`.

Модели требуют скачивания при первом использовании.
Сырые английские запросы остаются в данных. Перевод маркируется машинным и не
считается независимо собранной русскоязычной человеческой разметкой.

## Оценка и защита от утечки

Человеческие запросы хранятся только в `labels/`, никогда не добавляются к
текстам индекса. Английский запрос и его русский перевод имеют один split
по изображению/группе. При явном включении синтетические VLM-запросы допускаются только в train.
В текущем `run_gpu.sh` после аудита они отключены из-за смысловых ошибок.
Captioning не получает исходные поисковые запросы. Тестовые картинки входят в
каталог кандидатов, но их пары с запросами не участвуют в градиентных обновлениях.

Метрики: Hit@1/5/10 (найден ли хотя бы один известный позитив), Recall@k
(доля известных позитивов), NDCG@k (учёт позиции и graded relevance при наличии),
MRR@10. При одном позитиве Hit@k=Recall@k — это ожидаемо. Интервалы считаются
bootstrap по группам изображений, не по коррелированным переводам каждого запроса.

Исходная разметка неполная: другой подходящий стикер может быть не отмечен.
Поэтому текущие метрики означают нахождение известного позитива и не заменяют
независимую человеческую оценку. Отчёт должен прямо это говорить.

Для следующей итерации запланирована независимая ручная проверка 100–200 русских
запросов: стикеры и открытки, эмоции, визуальные объекты, точные надписи, смешанные
условия, отсутствие релевантного результата. Объединить top-10 нескольких методов,
убрать повторы, перемешать, оценить 0/1/2. Не объявлять синтетические запросы gold.
Отдельно учитывать иронию, отрицание и культурные отсылки.

Скрипт принимает `qrels` в записи запроса (item_id→0/1/2); `positive_item_ids`
должен соответствовать всем qrels>0. Для строгого image-disjoint протокола все
позитивы запроса должны относиться к его split. Другой протокол требует отдельной
явной реализации, его нельзя смешивать с этим автоматически.

Время в `metrics.json` — scoring + top-k на прогретых векторах. Оно НЕ включает
кодирование текста и загрузку изображения. В демо таймер охватывает кодирование и scoring, но не отрисовку картинок и сеть.

## 5. Демо и генерация

```bash
export STICKER_CATALOG=data/catalog
export STICKER_INDEX=runs/full_v2/index
export STICKER_CHECKPOINT=runs/full_v2/adapter/best.pt
python -m streamlit run app.py --server.address 0.0.0.0
```

Без обученного checkpoint не задавайте STICKER_CHECKPOINT. Для базового индекса
задайте STICKER_INDEX=runs/image_index. Для GPU-генерации:

```bash
python -m sticker_search.generate 'весёлый кот с чашкой кофе' \
  --output runs/generated/coffee_cat --seed 42
export STICKER_ENABLE_GENERATION=1
```

Сохраняются оригинал, вырезанный PNG и параметры. Точность русских надписей при
генерации не обещается: текущий генератор создаёт стикеры без текста. Предусмотрен
ручной выбор «не нашлось подходящего». Автоматический порог отсутствия ответа
нужно калибровать на размеченных no-match запросах; произвольный cosine-порог
не представлен как вероятность релевантности.

## План защиты (10–12 минут + вопросы)

1. Задача, сценарии, ограничения и источники — 2 минуты.
2. EDA, дубликаты и разбиение — 2 минуты.
3. Базовая модель, обучаемые части, loss — 2 минуты.
