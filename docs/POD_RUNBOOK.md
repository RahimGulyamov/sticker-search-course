### 5.1. Восстановление 16 ошибок языкового валидатора в старом пилоте

В присланном логе 16 из 500 ответов отклонены с `Invalid OCR language`: модель
вернула коды `ja`, `ko`, `pt`, `it`, `es`, `id`, `ar`, которых не было в enum.
Это не ошибка CUDA и не обрезанный JSON. Исправленный парсер сохраняет исходное
значение в `ocr_language_raw`, а дополнительные коды относит к `other`.
Определение языка и OCR остаются предсказаниями модели, а не проверенными фактами.

После замены `sticker_search/annotate.py`, когда workers остановлены, выполнить:

```bash

  --output runs/captions_500 --recover-errors
python -m sticker_search.annotate --task caption --catalog data/catalog \
  --output runs/captions_500 --merge
python -m sticker_search.review_annotations --catalog data/catalog \
  --annotations runs/captions_500/annotations.jsonl --output runs/review_500.html
```

Ожидается `Recovered 16 saved responses without inference; complete 500/500`.
При повторном вызове число восстановленных будет 0. Старые успешные строки,
конфигурации и error-логи сохраняются; добавляется происхождение восстановленных

по-прежнему не принимается, а merge требует полного покрытия.
Использовать исходные `errors-rank*.jsonl` на поде, не копию из Markdown.

Восстановление не меняет старые слабые запросы. В логе обнаружены вопросы про

### 5.2. Продолжить после 30 863 / 30 914

Полный первый проход завершился, но 51 ответ не прошёл JSON/schema-проверку.
В присланном логе видны `No JSON object in response`, неэкранированные управляющие
символы и название языка `punjabi`. Отсутствие JSON само по себе не доказывает
обрезание по лимиту токенов: нужен исходный response для точной классификации.

Патч v3 не меняет CAPTION_PROMPT и исходные worker-конфигурации:

- Парсер допускает буквальные переносы строк/табуляцию в JSON-строках, сохраняя
  текст. Незакрытый JSON и отсутствующие обязательные поля по-прежнему отклоняются.
- Известные названия языков, включая `punjabi`, нормализуются; сырое значение
  остаётся в `ocr_language_raw`.
- `--retry-missing` позволяет увеличить только `max_new_tokens`, сохраняя данные,
  prompt, модель, ревизию, число workers и разрешение. Повторяются только
  отсутствующие ключи; их новые параметры записываются в `generation`.
- Исходные тайминги и `config-rank*.json` не перезаписываются. Для retry создаются
  отдельные параметры и тайминги.

Обновлённый `run_gpu.sh` сначала повторно разбирает error-логи на CPU, затем
запускает остаток с `--max-new-tokens 1024 --batch-size 4` на тех же четырёх GPU.
Готовые 30 863 ответа не генерируются заново. Повторять исходный проход с тем же
лимитом 384 не требуется.

Если после retry останутся невалидные ответы, merge с явным
`--max-missing-fraction 0.005` разрешает не более 0,5% отсутствующих описаний.
Каталог изображений не меняется: для этих изображений индекс использует только
визуальные эмбеддинги, caption/OCR-ветви остаются пустыми. Это не фиктивная разметка
и не удаление сложных картинок из оценки. `coverage.json` содержит точное число,
долю и список пропусков. В отчёте нужно явно указать фактическое покрытие, в том
числе отдельно по стикерам и открыткам, и наличие fallback.
Без этого аргумента merge остаётся строгим. Для переводов частичный merge запрещён.

### 5.3. Продолжить после 4 122 / 4 171 переводов

По логу 28 сентября 12:59 МСК caption-этап завершён: 30 875 валидных описаний,

Режим `--from translate` полностью пропускает caption-стадию. Переводы сначала

конфигурации с лимитом 96 сохраняются, новый бюджет записывается в retry metadata.

При успешном строгом merge будут 4 171 перевод, после чего скрипт продолжит

этот файл для диагностики; одного общего `Incomplete annotation` недостаточно.
Непереведённые запросы не удаляются из русской оценки молча, английский оригинал
не маркируется русским переводом.

Теперь доступны точки продолжения `--from caption|translate|index|train|evaluate`.
Каждая запускает выбранный этап и следующие. Предыдущие артефакты должны быть
готовы. Для отдельного нового обучения нужны новый output/checkpoint-путь;
`--from train` не возобновляет состояние оптимизатора поверх существующего best.pt.

В поставленной разметке 2 883 исходных train-запроса. После полного перевода
будет 5 766 train-строк; переводы не являются независимыми человеческими метками.
Исходный английский dev содержит 608 запросов. Русский dev — их машинные переводы,
что не заменяет отдельную человеческую оценку русского поиска.

Это один опыт с lr=1e-3, rank=64 и 10 эпохами. Эпоха выбирается по объединённому
EN/RU dev, отчёт дополнительно разделён по языкам. Веса backbone заморожены.
Сравниваются `image`, `hybrid`, `lexical`, `learned` на одном каталоге и одинаковых
запросах внутри каждого языка. Test в этом скрипте не открывается.
Число изображений само по себе не означает такое же число размеченных пар.

Если `best.pt` остался от эпохи 0, обученные обновления не улучшили выбранную
метрику dev; это допустимый, честно фиксируемый результат. Следующими опытами
могут быть rank=16, lr={1e-4,3e-4} и ограниченная доля очищенных слабых меток.

Из четырёх A100 все четыре работают на разметке и переводе; индекс и адаптеры —
на одной GPU. Генератор из шага 7 проверяется отдельно, когда разметка закончена.

Caption/translation при повторном запуске используют успешные записи. После
завершённого обучения повторный train остановится из-за существующего `best.pt`;
это защита от перезаписи эксперимента, не resume оптимизатора. При необходимости
повторить только dev-оценку:

```bash
for query_lang in en ru; do
  python -m sticker_search.evaluate --index runs/full_v2/index \
    --queries "runs/full_v2/queries_$query_lang" \
    --checkpoint runs/full_v2/adapter/best.pt \
    --methods image hybrid lexical learned --split dev \
    --output "runs/full_v2/dev_$query_lang"
done
```

После выбора окончательной конфигурации провести отдельную оценку на test,
изменив `--split dev` на `--split test` и сохранив результат в новый каталог
`test_en`/`test_ru`. До фиксации выбора не подбирать параметры по test.

Локально проверены синтаксис Bash/Python и соответствие строк запросов векторам
при разбиении по языкам. GPU-прогон полного корпуса выполняется на поде.

## 7. Генерация и материалы для следующего шага

```bash
python -m sticker_search.generate 'весёлый кот с чашкой кофе' \
  --output runs/generated/coffee_cat --seed 42
```

Для анализа передать `runs/full_v2/dev_en/metrics.json`, `dev_ru/metrics.json`,

а для проблем CUDA — также `nvidia-smi` и вывод проверки torch из шага 1.
